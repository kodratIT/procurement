# Plan: Refaktor Workflow Stages Dinamis & Perbaikan History + Tombol Batal/Tolak/Perbaikan

**Tanggal:** 2025-09-05  
**Peminta:** workflow stages tidak sesuai aturan, marketing-only langsung complete setelah kadiv approve, history tidak informatif, butuh tombol Batalkan/Approve/Tolak/Butuh Perbaikan yang workflow-aware

## 1. Konteks & Masalah Tervalidasi

### 1.1 Workflow Stages Tidak Sesuai Aturan
- **Expected:** PR `marketing-only` 4 stage `Acc Kepala Divisi (11) -> Acc Manager Sales (12) -> Review Purchasing (13) -> Acc Keuangan (4)` sekuensial `approved` lanjut ke next stage (`WorkflowResolver.php:139`, `ApprovalActionService.php:232` `advance()`), baru `completed` setelah step terakhir.
- **Actual:** Setelah buat `custom-flex-test`/`marketing-only` PR langsung `approved` setelah kadiv approve. Penyebab: `workflow_steps:7,10,11` `is_required=0` (kita set untuk bypass missing-approver) -> `ApprovalInstanceCreator.php:78` `status=skipped` -> `advance()` tidak buka next stage -> langsung `setTerminalStatus(approved)` (cek `PR-202609-0005` logs `approval_advance` tidak ada, langsung `approved`).
- **Root cause:** `ApproverMapping` missing untuk `MANAGER_SALES`/`PURCHASING` (0 `user_assignments`) dan `KEUANGAN` `department_id=9` vs `user_assignment:8` `department_id=NULL` -> `WorkflowResolver.php:418` no match -> `missing_approvers` -> `handoff` diblock. Workaround kita ubah `is_required=0` bikin workflow "palsu" selesai dini.

### 1.2 History Tidak Informatif
- `PurchaseRequestInfolist.php:242-414` merge `purchase_request_status_histories` + `activity_log`. Label hardcode `timelineEventLabel()` `Diajukan/Review Purchasing/Menunggu persetujuan` + generic `Status berubah dari ...` (`timelineStatusDescription()`), tidak sebut `stage`/`approver`/`alasan`. Contoh: `Auto handoff to workflow after submit (bypass procurement).` tidak jelas bypass kenapa.
- `PurchaseRequestTimeline.php:36` `record()` simpan `note` tapi `ApprovalActionService::advance()` note `Moved to next workflow stage: {label}` tidak masuk `statusHistories.note` untuk PR.

### 1.3 Tombol Tidak Lengkap / Semantik Salah
- `ViewApprovalInbox.php:24-51` cuma `Approve`/`Reject` (English, `requiresConfirmation` `Textarea required`). Tidak ada `Batalkan (cancel -> draft/cancelled)`, `Butuh Perbaikan (return -> returned ke pengaju, bisa koreksi & resubmit)`, label `Tolak` seharusnya `reject -> rejected` (buat baru, bukan koreksi). `ApprovalActionService.php:26` `ACTIONS=[approve,reject,return]` dukung `return` tapi tidak di-expose.
- Semantik yang diminta: `Batalkan = draft tidak lanjut`, `Perbaikan = returned ke pengaju (ProcurementRequestDraftSaver::save + submit)`, `Tolak = rejected tidak bisa lanjut harus buat PR baru`, `Setujui = lanjut next stage sesuai workflow`.
- `PurchaseRequestPolicy.php` & `ProcurementReviewService.php` hardcode `allowed=[submitted, procurement_review]` + `isDynamicStage` tambahan, tapi belum sinkron dengan `cancel` permission.

## 2. Tujuan Refaktor Serius
- Semua status PR dinamis dari `workflow_steps.step_key` (`WorkflowStageService.php:77` `stageKeysFor()`), bukan hardcode `pending_approval/procurement_review`. Workflow baru otomatis kepakai tanpa ubah `PurchaseRequestStatus` enum.
- `PR.workflow_reference` dinamis per `ProcurementCategory.workflow_reference` (sudah `WorkflowResolver.php:64` fallback `standard-procurement`), `orderedStages = [draft, submitted, ...step_keys..., approved]` (`WorkflowStageService.php:90`).
- Tombol 4 aksi dengan semantik benar + history informatif per stage.
- `PR->status` selalu = `current pending step_key` (set di `handoffToApproval` & `advance()`), `timelineEventLabel` tunjuk nama stage.

## 6. Risiko & Mitigasi

- **Data `is_required=0` sekarang:** Kembalikan ke `1` butuh approver lengkap, jika SDM belum ada workflow akan block `can_handoff`. Mitigasi: fallback `role` atau buat user dummy dulu, atau keep `is_required=0` untuk step opsional dengan kondisi `gte 10jt`.
- **Activity log duplikat:** Pastikan `Infolist::timelineEntries` tidak filter `after.status` untuk status dinamis, biar tidak hilang.
- **Budget check `finance_approval`:** `ApprovalActionService::assertBudgetCheckPassed()` cek `workflow_settings.budget_check` untuk `Acc Keuangan` final, jangan skip.
- **Permission:** `Batalkan` butuh `canUpdate` + `cancel` policy, jangan beri ke approver yang tidak berhak.

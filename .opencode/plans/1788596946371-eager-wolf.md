# Plan: Agregasi Lintas Assignment Tanpa Switching

## Keputusan Pengguna

- Semua resource yang terkait kantor ikut menampilkan data lintas assignment aktif.
- Permission memakai union: data/action tersedia jika salah satu assignment aktif user mengizinkannya.
- Pembuatan PR memakai picker assignment/kantor pada form.
- Switcher kantor di topbar dihapus dari UI.

## Kondisi Saat Ini

`AccessContextService` menyimpan satu `active_context` di session dan `OfficeScoped`/`ContextScoped` menerapkan `scopeForCurrentContext()`. Akibatnya query resource hanya mengambil kantor, branch, dan department dari assignment aktif. `PurchaseRequestResource`, stats, export, Budget, Vendor, Purchase Order, Sample Shipment, Distribution, Invoice, Office, Procurement Category, dan User Assignment masih memiliki pola ini.

Approval Inbox sudah agregat melalui `ProcurementReviewService::reviewQueue()`, `ApprovalTaskLifecycleService::pendingTasks()`, dan query dasar `withoutGlobalScopes()`. Namun `ProcurementReviewService::assertReviewContext()` masih mengharuskan assignment session tunggal.

Fondasi authorization yang dipakai:

- `app/Services/AccessContextService.php`: daftar assignment aktif dan default context.
- `app/Services/MultiOfficeAuthorization.php`: `scopeForCurrentContext()` dan `scopeForUser()`.
- `app/Models/Concerns/OfficeScoped.php`: global scope untuk `PurchaseRequest` dan `SampleShipment`.
- `app/Models/Concerns/ContextScoped.php`: global scope untuk branch, department, cost center, batch, dan pilgrim.
- Filament `5.7.7`, Laravel `13.29.0`, PHP `8.5`.

## Desain yang Direkomendasikan

### 1. Pisahkan Read Aggregation dari Legacy Global Scope

Jangan mengubah global scope `OfficeScoped` atau `ContextScoped` menjadi agregat. Query internal, command, dan proses write tetap aman dengan perilaku single-context legacy.

Perkuat `MultiOfficeAuthorization::scopeForUser()` agar:

- Selalu melepas global scope `office` dan `access_context` sebelum menerapkan union.
- Mengambil hanya assignment aktif dan valid tanggal.
- Mengabaikan assignment yang tidak memiliki permission resource yang diminta.
- Menghasilkan grup OR per assignment: kantor wajib sama, branch/department yang terisi wajib sama, nilai null menjadi wildcard.
- Menghormati `assignment_scopes` untuk kategori pada model yang memiliki `category_id`; assignment dengan scope kategori hanya dapat melihat kategori yang diizinkan.
- Mengembalikan query kosong jika tidak ada assignment yang diizinkan.
- Memakai nama kolom ter-qualify agar aman pada relationship/subquery.

Tambahkan API eksplisit untuk authorization lintas assignment, misalnya `allowsAcrossAssignments()`/`canViewAcross()`, dan gunakan API ini untuk read/detail. Authorization mutation record juga harus mencari assignment aktif yang cocok dengan kantor/branch/department/category record, sehingga aksi di kantor kedua tidak lagi memerlukan session switch. Permission tetap dievaluasi union, sedangkan subject tetap harus cocok dengan scope assignment.

`requiresConfirmation()` tidak lagi menjadi syarat wajib untuk aksi cross-office karena switcher dan alur konfirmasi session dihapus. Target kantor sudah eksplisit dari record atau picker form. Pertahankan method/session lama hanya jika masih diperlukan oleh compatibility internal, tetapi jangan dipakai sebagai gate read/action baru.

### 2. Agregasikan Semua Resource Kantor

Ganti query resource berikut dari `scopeForCurrentContext()` ke `withoutGlobalScopes()`/`scopeForUser()` yang sesuai permission:

- `app/Filament/Resources/PurchaseRequestResource.php`
- `app/Filament/Resources/Budgets/BudgetResource.php`
- `app/Filament/Resources/VendorResource.php`
- `app/Filament/Resources/PurchaseOrders/PurchaseOrderResource.php`
- `app/Filament/Resources/SampleShipments/SampleShipmentResource.php`
- `app/Filament/Resources/Distributions/DistributionResource.php`
- `app/Filament/Resources/Invoices/InvoiceResource.php`
- `app/Filament/Resources/Offices/OfficeResource.php`
- `app/Filament/Resources/ProcurementCategoryResource.php`
- `app/Filament/Resources/UserAssignments/UserAssignmentResource.php`

Untuk resource yang sudah menggunakan `acrossOffices()`/`acrossContexts()` seperti Quotation, Pilgrim, Branch, Department, Cost Center, dan Umrah Batch, pertahankan pola tersebut dan audit agar tidak ter-AND kembali oleh global scope.

Untuk Distribution yang melakukan filtering melalui relasi batch, lepaskan global scope relasi sebelum menerapkan `scopeForUser()`. Untuk Sample Shipment, pertahankan aturan visibility receiver office dan gabungkan secara eksplisit dengan sender/owner assignment dalam grup query OR agar tidak terjadi kebocoran akibat `orWhere` tanpa grouping.

Ubah permission `canAccess()`/`canViewAny()` resource agar menu muncul bila ada assignment mana pun yang memiliki permission, bukan hanya assignment session aktif. Detail policy `view` juga harus mengizinkan record dari kantor assignment lain jika subject cocok. Mutation policy menggunakan permission union yang sama, tetapi tetap memvalidasi subject.

### 3. PR List, Stats, Tabs, Export, dan Approval

Pada `PurchaseRequestResource::getEloquentQuery()` gunakan query agregat dengan permission `ViewAny:PurchaseRequest`. Karena table PR tetap memakai `filterByRequester: true`, hasilnya tetap "PR milik saya" tetapi mencakup semua kantor. Kolom kantor yang sudah ada menjadi pembeda.

Pada `PurchaseRequestStats::scopedQuery()` gunakan query agregat lalu pertahankan filter `requester_id`. `ListPurchaseRequests::tabQuery()`, badge status, dan export CSV akan ikut hasil agregat tersebut. Pertahankan tab dan header-filter yang sudah ditetapkan pada `.ai/rules/approval-inbox.md`.

Approval Inbox tetap mempertahankan kontrak `.ai/rules/resources.md`:

- Tab aktif berisi tugas pending dan review yang dapat ditindaklanjuti.
- Arsip hanya berisi PR yang pernah di-approve oleh user login.
- PR rejected, returned, cancelled tidak masuk arsip.
- Aksi hanya tersedia pada task aktif.

Ubah `ProcurementReviewService::assertReviewContext()` agar mencari semua assignment reviewer dengan permission UPDATE yang cocok dengan office/branch/department/category request. Dengan demikian reviewer dapat forward, handoff, return, dan edit PR dari kantor lain tanpa switching. Jangan mengubah `WorkflowResolver`: resolver sudah berbasis office request dan snapshot workflow.

### 4. Picker Assignment untuk Pembuatan PR

Jangan memakai `office_id` saja sebagai identifier karena satu kantor dapat memiliki beberapa assignment berbeda. Pada `PurchaseRequestForm` tambahkan select create-only bernama `assignment_id`, dengan label dan opsi yang menampilkan kantor, branch, department, dan role. Opsi hanya berasal dari assignment aktif yang memiliki permission CREATE. Jika hanya ada satu opsi, tampilkan sebagai nilai default/field tersembunyi sesuai pola form yang ada.

Field assignment dibuat `live()` sehingga field dependent memakai konteks assignment pilihan. Cost center, batch, category, dan pilihan organisasi lain harus mengambil data lintas konteks yang tetap difilter ke target assignment, bukan global scope kantor aktif.

Pada `ProcurementRequestDraftSaver`:

- Untuk create, validasi `assignment_id` terhadap assignment aktif milik user dan permission CREATE.
- Ambil `office_id`, `branch_id`, dan `department_id` dari assignment tervalidasi, bukan dari session.
- Validasi cost center berada di kantor target dan aktif.
- Tolak assignment/office palsu, expired, disabled, atau tanpa permission.
- Untuk edit, pertahankan kantor/branch/department record dan cari assignment UPDATE yang cocok; jangan izinkan pemindahan kantor lewat edit.
- Biarkan `PurchaseRequest` tetap menyimpan snapshot organisasi pada record.


### 5. Hapus Switcher Topbar

Hapus render hook `TOPBAR_START` dan penggunaan view `filament.office-context` dari `app/Providers/Filament/AdminPanelProvider.php`. Hapus view topbar setelah tidak ada consumer. Route/controller switch boleh dipertahankan sementara hanya bila compatibility test atau session lama membutuhkannya, tetapi tidak lagi ditampilkan atau diperlukan untuk membaca/mengubah record.

`EnsureActiveOffice`/`EnsureAccessContext` tetap memastikan user memiliki minimal satu assignment aktif. Service masih boleh memilih default context untuk compatibility dan metadata, tetapi tidak boleh membatasi query agregat.

### 6. Authorization Service dan Caching

Tambahkan helper di `AuthorizationService` untuk query/permission union agar resource tidak mengulang implementasi. Bedakan jelas API:

- `scopeForUser`/`allowsAcrossAssignments`: read atau target permission lintas assignment.
- `scopeForCurrentContext`: compatibility untuk query legacy/internal yang memang membutuhkan context aktif.
- Targeted mutation authorization: assignment aktif mana pun yang cocok dengan record.

Jangan menambah cache global yang dapat mencampur user atau request. Jika query assignment di-cache per request, gunakan binding scoped yang sudah dipakai aplikasi dan pastikan permission override, tanggal validitas, dan perubahan assignment tidak stale lintas request.

## Test Plan

Buat atau perbarui feature tests dengan PHPUnit sesuai pola test yang sudah ada:

1. User dengan dua kantor dan permission berbeda melihat record dari kedua kantor sesuai union permission; user tanpa assignment yang cocok tidak melihat record.
2. Branch/department assignment yang spesifik tidak melihat record branch/department lain; assignment null tetap wildcard.
3. Assignment dengan category scope hanya melihat kategori yang diizinkan.
4. Detail record dari kantor non-default dapat dibuka tanpa `setContext()`/POST switch.
5. Semua resource kantor utama mengembalikan record dari assignment A dan B; resource yang sudah agregat tidak regress.
6. PR stats, status tabs, table, filter kantor, dan CSV export menghitung/menampilkan gabungan kantor tanpa mencampur PR milik user lain.
7. Reviewer dengan assignment UPDATE di kantor B dapat menjalankan review/handoff dari context default kantor A.
8. Approval Inbox tetap memisahkan aktif/arsip dan tetap menyembunyikan rejected/returned/cancelled dari arsip.
9. Create PR dengan assignment B menyimpan office/branch/department B tanpa mengganti session context; assignment expired, unauthorized, atau office palsu ditolak.
10. Edit PR tidak dapat memindahkan office dan hanya dapat dilakukan oleh assignment UPDATE yang cocok.
11. Topbar switcher tidak lagi dirender, tetapi panel tetap dapat dibuka user dengan minimal satu assignment aktif.

Jalankan test paling sempit terlebih dahulu, lalu suite terdampak:

Verifikasi manual di panel admin: login user multi-kantor, pastikan list PR/Budget/Vendor/PO/Shipment/Distribution/Invoice menampilkan kantor A dan B tanpa switching, create PR memilih assignment B, dan approval/review dari kedua kantor muncul pada satu inbox. Periksa `browser-logs` jika ada error Livewire/Filament.

## Risiko dan Mitigasi

- **Kebocoran data karena `whereIn(office_id)` sederhana:** gunakan OR group dari `scopeForUser()` agar branch, department, category, dan permission tetap dihormati.
- **Global scope tetap menempel:** helper agregat harus melepas `office` dan `access_context` sebelum menambahkan union.
- **Assignment sama kantor tetapi role berbeda:** picker memakai assignment id, bukan office id saja.
- **Aksi mutation lintas kantor:** selalu cocokkan subject record dengan assignment aktif yang memiliki permission; jangan mengandalkan session.
- **Relasi dengan office scope:** audit `whereHas`, eager load, exporter, dan relation manager agar tidak kembali ke context aktif secara tidak sengaja.
- **Query OR terlalu besar:** gunakan index yang ada terlebih dahulu, ukur dengan `EXPLAIN`, lalu tambahkan migration index hanya bila diperlukan.
